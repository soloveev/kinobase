# Кино База

Персональная база фильмов одного зрителя. Главная — сетка постеров с фильтрами и статусами: что посмотрено, что в планах, чего ждём. У каждого тайтла своя страница: справка (название, дата выхода, создатели, аннотация, теги, рейтинги), личные поля владельца и агентское досье — «Зачем смотреть» до просмотра, «Важные вещи о фильме» и разбор «После просмотра» после. Рядом живут страницы создателей: не биография со списком наград, а творческий метод человека и разбор того, как этот метод сработал в отдельных работах.

Наполняет базу агент, а не форма. Формы добавления в интерфейсе нет и не будет: справочные данные и тексты досье лежат в файлах `content/*.json`, оттуда их переносят в базу скрипты наполнения, а собирает их агент по скиллам из `.agents/skills/`. Через интерфейс правятся только личные поля — оценка, звёздочка, комментарий, отметки «посмотрел» и «хочу посмотреть». Всё остальное правится в файлах и прогоняется скриптом: правка справочного поля прямо в базе молча откатится при следующем прогоне.

Этот репозиторий — отчуждаемая версия базы: её клонируют, разворачивают локально, наполняют своими фильмами и выкатывают на свой VPS. Владелец базы — тот, кто её у себя поднял. Локально владельцем считается любой посетитель; разделение гостя и владельца работает только в боевой сборке. В репозитории лежат пять демонстрационных тайтлов — чтобы сайт был живым с первой минуты и чтобы у агента был образец, на который равняться.

**Первый заход — по скиллу `kinobase-setup`: сначала развернуть и показать, вопросы потом** (`.agents/skills/kinobase-setup/SKILL.md`).

## Скиллы

Канон — папка `.agents/skills/` в открытом формате Agent Skills: каждый скилл лежит своей папкой с файлом `SKILL.md`, у которого есть фронтматтер с именем и описанием. `.claude/skills` — символическая ссылка на неё, так что Claude Code видит те же самые файлы. **Агент без поддержки скиллов открывает нужный `SKILL.md` и читает его как инструкцию** — ничего сверх обычного чтения файла для этого не требуется.

| Скилл | Файл | Когда применять | Модель |
|---|---|---|---|
| `kinobase-setup` | `.agents/skills/kinobase-setup/SKILL.md` | первый заход в репозиторий: развернуть, показать, затем онбординг | любая |
| `film-card` | `.agents/skills/film-card/SKILL.md` | завести или дозаполнить справочную карточку: поля, идентификаторы, аннотация, постер, теги, сезоны | Sonnet или другая средняя: здесь сверка, а не суждение |
| `film-dossier` | `.agents/skills/film-dossier/SKILL.md` | собрать материалы к фильму: «Зачем смотреть», «Важные вещи о фильме», разбор «После просмотра» | Opus или другая сильная: агент утверждает нечто от своего лица |
| `creator-dossier` | `.agents/skills/creator-dossier/SKILL.md` | завести страницу создателя: справка, творческий метод, разбор работ | Opus или другая сильная: метод — это суждение |
| `exa-tabstack-search` | `.agents/skills/exa-tabstack-search/SKILL.md` | любая работа в вебе: поиск, чтение страниц, добор источников | любая |
| `full-file-read` | `.agents/skills/full-file-read/SKILL.md` | гарантированное чтение большого файла целиком, когда полнота критична | любая |

Источник правды по модели — строка «Модель:» в самом `SKILL.md`. Поисковые сервисы ни одному скиллу не обязательны: чем именно эта база ищет и читает, записано в `research/SEARCH-PROFILE.md`, и без ключей агент работает встроенными инструментами.

## Данные

- **Схема — только через миграции Drizzle.** Дописанный руками `UPDATE` в файле миграции сотрёт следующий `npm run db:generate`.
- **Копия базы снимается вместе с `-wal` и `-shm`** либо командой `sqlite3 data/kinobaza.db ".backup копия.db"`. База работает в режиме WAL, и обычный `cp` даёт отставший снимок. Перед миграцией на живой базе — копия, после — сверка.
- **Локально база всегда своя.** Вне боевой сборки `viewerIsOwner()` возвращает `true` без всякого входа. Разделение гостя и владельца живёт только в production, и тесты на него объявляют боевое окружение явно.
- **Личные поля — оценка, звёздочка, комментарий, «посмотрел», «хочу посмотреть» — самое ценное в базе.** Скрипты наполнения их не трогают ни при каких условиях. **Путь записи один — `updatePersonalAction`**: правила «оценка означает просмотр», «отметки взаимоисключающи», «невышедшее не оценивается» живут в `src/lib/films-repo.ts` и достаются каждой поверхности правки даром. Новая поверхность переиспользует это действие, а не пишет похожее рядом.
- **«Посмотрел» и «Хочу посмотреть» взаимоисключающи.** Постановка одной отметки снимает вторую, снятие «Посмотрел» снимает и оценку. Держится сервером, а запрещённые состояния в уже занесённых данных показывает `npm run check-db`.
- **Комментарий владельца виден всем, но остаётся личным полем.** Пустой комментарий хранится как `null`, к этому приводит валидатор.
- **Справочные поля через интерфейс не правятся нигде.** Справка едет из `content/*.json` скриптами наполнения; правка прямо в базе откатится следующим прогоном `refresh-films` или `tag-films`.
- **Фильм в скриптах наполнения ищется по оригинальному названию, а не по русскому** — одинаковые русские названия в базе норма. В `titleRu` не пишутся ни год, ни пометка формы: год приписывается при показе. Ключ тайтла — `filmKey` из `src/lib/film-key.ts`, второй копии этого суждения в проекте быть не должно.
- **Теги и сезоны продублированы** между `films-data.json` и `tags-data.json` / `seasons-data.json`. Менять оба файла и прогонять `npm run check-data`: правка одного молча откатится.
- **Персоналию нельзя оценить.** Запрет держится схемой — у таблицы `people` нет колонок личных полей.
- **Живые проверки в браузере пишут в рабочую базу.** Автоматизацию браузера и клики по личным полям гонять на отдельной базе, задав `DB_PATH`.

## Тексты

Тексты пишутся по шести файлам-основаниям в `research/`: как ищем (`SOURCING.md`), как проверяем (`VERIFICATION.md`), что законно (`LEGAL.md`) и три формы записи — карточка, досье, страница создателя. Читаются они до письма, а не после.

- **Правовая рамка обязательна** и действует на всё, что видит читатель, включая аннотацию справочной карточки. Это требование закона, а не редакторский вкус. Общие принципы — в `LEGAL.md`; местное право владельца базы вполне может требовать большего, и дополнить файл под свою юрисдикцию — его обязанность.
- **Утверждение не может быть увереннее своего статуса.** Статус едет вместе с фактом в любой блок текста. Совпадение по времени — не причинность.
- **Весь агентский текст, который видит читатель продукта, проходит редактора** — аннотации, «Зачем смотреть», «Важные вещи о фильме», «После просмотра», страницы создателей. Редактор — отдельный проход, а не стилист; правила и его право флага описаны в `research/VERIFICATION.md`, раздел «Редактор — третий проход, а не стилист». Текст владельца от первого лица — комментарии к фильмам — редактора не проходит: у авторского текста есть автор, и спорить с редактором в нём некому. Проектная документация тоже не его дело.

## Код

- Простота прежде всего, YAGNI: функциональность будущих версий заранее не закладываем, осиротевший код удаляем вместе с тестами.
- Следовать конвенциям файла и проекта, а не привносить свои. Комментарий — только там, где код не может объяснить «почему».
- TypeScript strict, без `any`. Ошибки не глотать. Валидация на границах системы, внутри доверяем типам.
- **Валидатор возвращает `null` при успехе**, иначе код ошибки — конвенция проекта (`validateTags`, `validateDossierBlock`, `validateSeasons`, `validatePerson`).
- **«Сегодня» считается на сервере и приходит пропом.** Клиентский компонент его не вычисляет — иначе разойдётся гидратация.
- **Пакеты со скриптами установки пришпилены в `allowScripts` к версии** (`better-sqlite3@13.0.3` и остальные). Это защита от чужого кода на установке, но у неё есть обратная сторона: подняли версию такого пакета — npm молча перестанет запускать его скрипт сборки и скажет об этом строкой, неотличимой от обычного предупреждения про `fsevents`. После такого обновления — `npm approve-scripts <пакет>` и проверка нативного модуля: `node -e "new (require('better-sqlite3'))(':memory:')"`.

## Тесты

- Тест — контракт: описывает поведение из правил, а не реализацию. Проверяем через публичный интерфейс, красный до имплементации и зелёный после.
- Быстрые и детерминированные: без сети, база — SQLite в памяти, «сегодня» передаётся аргументом.
- **Проверять число собранных файлов и тестов, а не цвет.** Под нагрузкой параллельный прогон выходит с нулевым кодом, не собрав часть файлов, и неполный прогон выглядит успехом. Прогон, которому верят, — `npx vitest run --no-file-parallelism`, и число файлов сверяется с прошлым.
- **Тест пишется на правильное поведение.** Известное ограничение — строка в списке задач, а не зелёный тест, закрепляющий это ограничение как норму.
- **CSS-поведение тестами не проверяется** — в jsdom Tailwind не загружен. Живой прогон в браузере обязателен.
- **Тесты не зависят от `src/site.config.ts` владельца.** `vitest.setup.ts` подменяет конфиг значениями свежего клона, поэтому заполненный онбордингом конфиг прогон не красит и выкатку не закрывает. Тесту с другими значениями — свой `vi.mock` того же модуля.

## Работа порцией

Правило действует всюду, где несколько агентов правят записи одного файла данных: досье, персоналии, карточки. Без него агенты затирают работу друг друга, и заметно это становится только на слиянии.

- **Каждый агент пишет только свой файл** вида `<работа>-<slug>.json` во временную папку порции и общего файла данных не касается. Имя файла несёт slug, потому что рабочая папка у параллельных агентов общая.
- **Копия старой записи уходит в архив порции до старта.** Из общего файла она исчезнет, а сверять потом будет не с чем.
- Разумная порция — три-четыре записи, между порциями читаются отчёты агентов: правила ломаются на живом материале, и видно это только из отчёта. **Отчёт агента приходит текстом** — субагент файл-отчёт записать не может, координатор кладёт его дословно рядом с порцией.
- **Координатор сверяет, что неизменные поля перенесены байт в байт**, вливает записи в общий файл и только после слияния гонит общие проверки.
- **Субагент в общем рабочем дереве не трогает git-состояние.** Ни `stash`, ни `checkout`, ни `reset`: откат ради собственной сверки откатывает чужую работу. Прежнюю версию файла смотрят через `git show HEAD:<файл>`.

## Git

Коммиты атомарные, сообщение — что и зачем. Коммитим только рабочее состояние: тесты и линтер проходят. Не коммитим секреты и сгенерированное: `.env*`, `deploy.env`, `*.db`, `data/`, `node_modules`, `.next`. Сырые архивы источников по фильмам (`research/<фильм>/`) в гит тоже не едут — из `research/` версионируются только файлы правил в корне.

## Демонстрационные тайтлы

Пять фильмов из `content/*.json` лежат в базе наравне со всеми остальными: «Одиссея» и «Из машины» — с полным досье, «Социальная расплата» — только с блоком «Зачем смотреть», «Оглянись» и «Оборотень» — только со справкой. Они же служат образцом тона и глубины, когда агент пишет первое своё досье.

Убрать их — попросить агента удалить эти записи из всех файлов `content/*.json` и постеры из `public/posters/`, после чего пересобрать базу: `rm data/kinobaza.db*`, затем `npm run seed` и остальные скрипты наполнения в порядке из `docs/ARCHITECTURE.md`. Личных полей в демо-записях нет, так что терять при этом нечего.

# Первый заход и онбординг

Скилл ведёт человека от свежего клона до живого сайта, а потом настраивает репозиторий под него. Порядок в нём важнее команд: **сначала развернуть и показать, вопросы потом**. Человек, который ещё не видел сайта, не знает, о чём его спрашивают.

Модель: любая. Работа механическая, суждение нужно в одном месте — как пересказать пользователю, что у него получилось.

Общий обзор проекта — в [AGENTS.md](../../../AGENTS.md); устройство кода и скриптов — в [docs/ARCHITECTURE.md](../../../docs/ARCHITECTURE.md).

## Первый заход

Вопросов на этом этапе не задаётся ни одного — ни про имя, ни про ключи, ни про сервер. Всё, что нужно для запуска, в репозитории уже есть.

### Шаг 1. Зависимости

```bash
npm install
```

Часть пакетов собирается из исходников (`better-sqlite3` — нативный модуль), так что первая установка занимает минуту-другую.

`npm install` на npm 11 может напечатать `npm warn allow-scripts … fsevents` — это предупреждение о скриптах установки, на `better-sqlite3` оно не влияет; проверить нативный модуль одной строкой: `node -e "new (require('better-sqlite3'))(':memory:')"`.

### Шаг 2. Окружение и токен владельца

```bash
cp .env.example .env.local
TOKEN=$(openssl rand -hex 24)
awk -v t="$TOKEN" '/^OWNER_TOKEN=/{print "OWNER_TOKEN=" t; next} {print}' .env.local > .env.local.tmp \
  && mv .env.local.tmp .env.local
grep '^OWNER_TOKEN=' .env.local
```

Последняя команда должна напечатать строку с 48 шестнадцатеричными знаками. Это секрет, по которому боевой сайт узнаёт владельца; локально он не нужен — вне боевой сборки владельцем считается любой посетитель. Файл `.env.local` в гит не едет.

### Шаг 3. База с демонстрационными фильмами

```bash
npm run seed           # строка вида «Занесено фильмов: 5»
npm run fill-dossiers  # строка вида «Досье записаны: 3 из 3»
npm run check-db       # строка вида «База чиста: 5 тайтлов…»
```

`npm run seed` открывает базу `data/kinobaza.db` (файл и папка создаются, схема накатывается при первом открытии — отдельного шага миграций нет) и заносит пять тайтлов из `content/films-data.json` вместе с тегами. Сид намеренно отказывается работать на непустой базе: повторное наполнение возможно только после того, как файл базы удалён вручную.

`npm run fill-dossiers` докладывает тексты досье из `content/dossier-data.json` — сид их не переносит. Остальные скрипты наполнения на демо-данных не нужны: `tag-films` пригодится, только если теги правились в `tags-data.json` отдельно от `films-data.json`, а `fill-seasons` и `fill-people` — когда в базе появятся сериалы и персоналии; сейчас оба файла пусты.

### Шаг 4. Сайт

```bash
lsof -tiTCP:3000 -sTCP:LISTEN   # пусто — порт свободен
nohup npm run dev > /tmp/kinobase-dev.log 2>&1 &
```

`nohup` — чтобы сервер пережил конец команды в оболочке агента.

Порт занят — поднять на соседнем: `PORT=3001 nohup npm run dev > /tmp/kinobase-dev.log 2>&1 &`, и дальше везде подставлять свой номер. Сервер оставляем работать: человеку сейчас показывать сайт.

Проверка, что главная отдаёт все пять постеров:

```bash
curl -s http://localhost:3000/ | grep -o 'posters/[a-z0-9-]*\.jpg' | sort -u | wc -l   # 5
```

Другое число или ошибка — смотреть `/tmp/kinobase-dev.log`, а не идти дальше.

### Шаг 5. Показать

Сказать человеку словами, не списком команд:

- адрес — `http://localhost:3000` (или тот порт, на котором сервер поднялся);
- что на сайте пять демонстрационных фильмов: у «Одиссеи» и «Из машины» собрано полное досье — «Зачем смотреть», «Важные вещи о фильме» и разбор «После просмотра»; у «Социальной расплаты» только блок «Зачем смотреть»; «Оглянись» и «Оборотень» заведены как справка, без материалов агента. Так и выглядит база в работе: у разных фильмов разная глубина;
- что личные поля — оценка, звёздочка, комментарий, отметки «посмотрел» и «хочу посмотреть» — правятся прямо на странице фильма, и локально для этого не нужно никакого входа: вне боевой сборки владельцем считается любой посетитель.

### Шаг 6. Предложить первый свой фильм

После показа — предложение, дословно по смыслу:

> Хотите завести свой фильм? Назовите его. Карточка — около десяти минут работы агента (замер автора, сентябрь 2026); полное досье — от 45 минут до двух с половиной часов по часам и от полутора миллионов токенов, персоналия не замерялась.

**Пока пользователь не назвал фильм, агент ничего не ищет и не заводит.** Ни «на пробу», ни «по мотивам демо», ни по спискам популярного. База персональная, и первый тайтл в ней выбирает её владелец.

Назвал — дальше работают скиллы наполнения: `film-card` заводит справочную карточку, `film-dossier` собирает материалы.

## Онбординг

Начинается после показа. Четыре вопроса. Если у агента есть инструмент вопросов с вариантами ответа — задавать по одному; если нет — одним сообщением, списком из четырёх пунктов, чтобы человек ответил разом.

| # | Вопрос | Куда ложится ответ |
|---|---|---|
| 1 | Как вас зовут — имя будет стоять в подвале сайта и под вашими комментариями к фильмам? Есть ли блог или канал, на который его сослать? | `src/site.config.ts`: `author`, а ссылка — `authorLink` (нет ссылки — оставить `null`) |
| 2 | Как назвать сайт? По умолчанию — «Кино База» | `src/site.config.ts`: `title` |
| 3 | Есть ли ключи поисковых сервисов — Exa, Tabstack, Parallel? Какие именно? | `.env.local` и `research/SEARCH-PROFILE.md` |
| 4 | Есть ли свой сервер и домен, куда базу выкатывать? | `deploy.env`, а домен — ещё и в `src/site.config.ts`: `url: 'https://<домен>'` (по нему собираются превью ссылок); нет — пропускаем, `url` остаётся локальным |

Имя пишется в именительном падеже: подвал и подпись ставят его после тире, склонений проект не заводит. Пустое имя даёт подпись «Владелец базы» — это рабочее состояние, а не ошибка.

Ключи из третьего ответа вписываются в `.env.local` — строки `EXA_API_KEY`, `TABSTACK_API_KEY`, `PARALLEL_API_KEY` там уже стоят пустыми из образца `.env.example`. Приложение их не читает: ключи нужны скиллу `exa-tabstack-search`, который перед запросами делает `set -a; source .env.local; set +a`. В `research/SEARCH-PROFILE.md` записывается ступень и перечень того, что есть: **полный** — все три сервиса, **частичный** — часть ключей, **встроенный** — ключей нет и агент ищет своими инструментами. Форму записи смотреть в самом файле: там таблица ступеней и объяснение, что каждая означает. Ни один скилл наполнения ключей не требует; от ступени зависит охват поиска, а не возможность работать.

Четвёртый ответ, если сервер есть: `cp deploy.env.example deploy.env` и заполнить `SSH_HOST`, `DOMAIN`, `SERVER_IP`; пути на сервере, пользователя и порт оставить как в образце, если нет причины менять — они совпадают с `ops/` и `docs/server.md`, после чего отправить человека к [docs/server.md](../../../docs/server.md) — там весь путь от чистой Ubuntu до HTTPS и шаблоны из `ops/`. Сервера нет — пропускаем без сожалений: локальный запуск самодостаточен, выкатку можно настроить когда угодно потом.

Токен владельца не спрашивается, и сказать о нём нужно даже когда сервера нет — значение из `.env.local` понадобится в день, когда сервер появится: он сгенерирован на втором шаге первого захода и лежит в `.env.local`. Объяснить человеку, что **то же самое значение** понадобится на сервере — в файле `/etc/kinobase.env` (образец — `ops/kinobase.env.example`), иначе боевой сайт не узнает владельца и покажет ему гостевой вид.

### Завершение

```bash
git status --short
```

Ожидание: изменены только `src/site.config.ts` и `research/SEARCH-PROFILE.md`. Даже при настроенном сервере ничего больше появиться не должно — `deploy.env` и `.env.local` перечислены в `.gitignore`. Что-то ещё в выводе — разобраться до того, как отдавать работу.

И последнее, что стоит сказать: пять демонстрационных фильмов можно оставить — они лежат в базе наравне с будущими своими и служат агенту образцом тона и глубины, — а можно попросить убрать. Как убирают, написано в `AGENTS.md`, раздел «Демонстрационные тайтлы».

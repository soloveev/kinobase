# full-file-read

Протокол гарантированного полного чтения файла. Применять, когда **полнота
покрытия критична** — иначе ответ окажется собран по куску, и часть
содержимого молча выпадет.

## Почему это вообще нужно

`Read(file_path)` без `offset`/`limit` имеет лимиты по токенам, размеру и
числу строк. Большой файл может быть прочитан **не до конца**, и tool не
обязательно сообщит об усечении. Если задача — «прочитай / разбери / выжми
тезисы / найди все упоминания», нужно явно подтвердить, что покрытие дошло
до последней строки.

## Когда применять (триггеры)

- Пользователь сказал «целиком», «полностью», «от начала до конца», «весь
  файл», «всё подряд», «все тезисы», «все упоминания», «не пропусти», «full»,
  «entire», «complete», «all of».
- Задача по своей природе требует полноты: конспект, ревью, аудит, извлечение
  всех тезисов/цитат/имён, поиск всех вхождений, сверка двух файлов целиком.
- Файл явно крупный (больше нескольких сотен строк или больше ~50 КБ) и его
  содержимое идёт в основу следующего шага.

Если задача — «найди мне функцию X», «процитируй абзац про Y», «исправь баг
в файле» — этот протокол **не нужен**, обычного `Read` достаточно.

## Протокол

### 1. Замерь файл

Перед любым чтением:

```bash
wc -l <file>          # сколько строк
wc -c <file>          # сколько байт
file <file>           # формат, если не очевиден из расширения
```

При необходимости — `head`, `tail`, `sed -n '1,5p'` чтобы увидеть структуру.

### 2. Выбери стратегию по типу

| Тип файла | Стратегия |
|---|---|
| Обычный текст / markdown / код | Chunking через `Read` с `offset`/`limit`. Размер чанка — по плотности текста (для кода ~500 строк, для markdown ~300, для плотного текста ~150–200). |
| JSON / XML | Сначала отформатировать (`jq .`, `xmllint --format`) или извлечь нужное (`jq '.path.to.field'`). Не читать одну гигантскую строку as is. |
| Minified JS/CSS, длинные логи | Сначала разбить или извлечь релевантное через `python`, `jq`, `rg`, `sed`, `awk`. |
| CSV/TSV/XLSX | Парсить через `python` (`pandas`/`csv`) или `xsv`/`miller`, не загружать целиком построчно. |
| `.docx`, `.pptx`, `.pdf` | Использовать соответствующие скиллы — у них свои тулзы. |

### 3. Читай партиями

Для текстовых форматов: вызови `Read` несколько раз с `offset` и `limit`,
покрывая весь диапазон `[1, total_lines]` без пропусков. Между чанками
держи в голове / в заметках, что уже прочитано.

### 4. Проверь покрытие (обязательный шаг)

После последнего чтения сверь: последний прочитанный `offset + limit ≥ wc -l`.
Если последний чанк закончился раньше последней строки — это **не
полное чтение**, дочитай хвост.

Не утверждай «прочитал файл целиком», пока покрытие не сверено.

### 5. Если файл слишком большой даже для chunking

- Делай **промежуточные саммари** по чанкам (1–2 предложения на чанк или
  список тезисов). Складывай их в рабочий контекст.
- В конце синтезируй общий вывод из саммари, а не из исходных чанков.
- Альтернатива: делегировать задачу субагенту (`Agent` / `Explore`) — у него
  свежий контекст. **Передай ему этот протокол явно в prompt**, иначе
  субагент сделает обычный `Read` и вернёт только часть.

## Анти-паттерны

- ❌ `Read(file_path)` без размерной оценки → «прочитал и сделал саммари».
  Проверка покрытия не сделана, часть файла могла выпасть.
- ❌ `cat file.json | head` для большого JSON — теряет структуру.
- ❌ Один `Read` на minified-файл — попадёт огромная одна строка, дальше
  ничего полезного не выжать.
- ❌ Делегировать subagent'у «прочитай и сделай саммари» без явной передачи
  full-file reading protocol.

## Шаблон для делегирования субагенту

Когда отдаёшь задачу субагенту, начни prompt с:

> Применяй full-file reading protocol: измерь файл через `wc -l`/`wc -c`,
> читай партиями через `Read(offset, limit)`, в конце сверь, что последний
> диапазон дошёл до последней строки. Не утверждай, что файл прочитан
> целиком, пока покрытие не сверено. Если файл слишком большой —
> накапливай чанковые саммари и синтезируй общий вывод из них.

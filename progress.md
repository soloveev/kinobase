# Хроника

## 2026-09-22 — Серверная инструкция прочитана придирчиво и переписана

Путь «от чистой Ubuntu до HTTPS» до сих пор никто не проходил чужими руками. Отдельный агент прошёл `docs/server.md` вместе с шаблонами `ops/`, `deploy.sh` и `package.json`, сверяя каждое утверждение с файлами. Четыре места останавливали человека или давали поломанный сайт, и все четыре починены.

После первой ручной сборки владелец каталогу кода не возвращался: перенос и сборка идут от root, служба работает под своим пользователем, и оптимизатор картинок не смог бы писать в `.next/cache` — страницы открылись бы, постеры нет. Теперь в шаге 4 стоит `chown`, а у ручного `rsync` появились `--no-o --no-g`. На сервере запускался только `seed`, без `fill-dossiers`: человек получил бы пять фильмов без единого блока досье — то есть без того, что показано на скриншотах README. Сертификат выпускался `certbot certonly --webroot` без хука на перезагрузку nginx: через два месяца файлы обновились бы, nginx остался со старым в памяти, и сайт начал бы отдавать просроченный — добавлен `--deploy-hook`. Плейсхолдеры `${SSH_HOST}` и прочие стояли прямо в командах, но нигде не объявлялись — в начале первого раздела появился блок `export`.

Отдельно снято противоречие про секрет владельца. Инструкция требовала возить `OWNER_TOKEN` с ноутбука на сервер, шаблон рядом предлагал сгенерировать новый. По коду прав шаблон: `/owner/login` кладёт в куку значение серверной переменной, а `src/lib/session.ts` сверяет куку с ней же — локальный секрет в бою не участвует. Решение владельца: секрет генерируется на сервере и никуда не ездит. Приведены к этому `docs/server.md`, `.env.example`, `ops/kinobase.env.example`, README и скилл `kinobase-setup`.

Дописано то, чего не было вовсе: порты и сетевой экран хостинга, отключение входа по паролю после установки ключа, `ssh-keygen` для тех, у кого ключа нет, адрес сайта в `src/site.config.ts` до первой сборки, готовая команда вместо ручного комментирования блока nginx, проверка на запись в конце установки, вынос копий базы за пределы сервера, ротация лога копий и чей именно crontab, проверка копии перед восстановлением, раздел про удаление демо-тайтлов с боевого сайта и три симптома в диагностике — `Killed` при сборке, падение `better-sqlite3`, непонятный отказ узнавать владельца.

## 2026-09-22 — Довезены скрипты блока ключей и сняты отсылки к specs/

Вторая проверка публикации искала не файлы, а указатели внутрь текстов, и нашла сорок четыре упоминания папки `specs/`, которой в отчуждаемой версии нет. Лишних файлов в репозитории при этом не обнаружилось. Три упоминания были рабочими указаниями и починены: `grep` по `specs/v1/films-data.json` в `SOURCING.md` стал `content/films-data.json`, из скилла `film-dossier` убрана отсылка к архиву спеки, в `tests/dossier.test.ts` путь к проверке ключей стал `scripts/keys-check.py`. Сорок остальных — сноски в комментариях тестов на спеки версий личного проекта; они оставлены как история, а в `AGENTS.md` появилось объяснение, что это такое и почему искать эти файлы не нужно.

Главное же: скилл `film-dossier` описывал порядок отдельной переписки блока «Важные вещи о фильме» через `keys-extract.py` и `keys-merge.py`, которых в репозитории не было — из четырёх питоновских помощников приехал один. Теперь приехали все: `scripts/keys-extract.py` достаёт разбор сплошным текстом, `scripts/keys-archive.py` кладёт копию нынешнего блока до старта порции, `scripts/keys-merge.py` вливает переписанные блоки обратно и сам стережёт неизменность `before`, `after`, `sources` и `searchedAt`. Общее у них — `scripts/lib/keys_common.py`, который слаг архива не считает сам, а берёт у `scripts/archive-slugs.ts`. Команды объявлены в `package.json`, описаны в README и `docs/ARCHITECTURE.md`; круг «достать — заархивировать — проверить — влить» прогнан на демо-записи «Из машины», файл данных после слияния совпал байт в байт.

## 2026-09-22 — Пятый цикл: тест с чистого GitHub и правки по его итогам

Проверка не клона рабочей папки, а публикации: агент без контекста склонировал репозиторий с GitHub в стороннюю папку и развернул его, имея только сам репозиторий. Установка, токен владельца, сид, досье, сайт, тесты, линтер и боевая сборка прошли без блокеров и без единого вопроса к владельцу; личные поля и режим гостя проверены в живом браузере. Нашлось восемь мест, которые чинятся: `next` поднят до 16.3.5 — в 16.3.2 критическая уязвимость Image Optimization API, — заодно закрыты high в `sharp` и `js-yaml`; ссылка переключателя в подвале стала «Вернуться к своему виду», потому что админки в этой версии нет; `keys-check` без аргумента печатает подсказку вместо тишины; в README появились Python 3 в требованиях и объяснение оставшихся moderate от `drizzle-kit`; в `docs/ARCHITECTURE.md` исправлено описание `AGENTS.md`, в `docs/posters.md` убрана ссылка на `kanban.md`, которого в публичной версии нет; в `AGENTS.md` записана ловушка с `allowScripts`.

## 2026-09-22 — Версия 1: отчуждаемая база

Собрана из персонального проекта автора вычитанием личного: без страницы «О проекте», админки и ссылок на канал; личные константы — в `src/site.config.ts`, файлы данных — в `content/`. Демо — пять фильмов: два с полным досье, один с блоком «Зачем смотреть», два только со справкой. Скиллы наполнения, правила текстов, шаблоны сервера и документация — в репозитории; поисковые ключи необязательны. Первый заход агента — `.agents/skills/kinobase-setup`.

Перед публикацией — четыре цикла проверки свежим агентом: чистый клон, агент без контекста разворачивает базу по `README.md` и скиллу `kinobase-setup`, проходит онбординг и сдаёт отчёт. По итогам циклов `.env.example` едет в гит, название сайта берётся из конфига везде, тесты не зависят от заполненного `src/site.config.ts` (мок в `vitest.setup.ts`), токен владельца берётся из локального `.env.local`. Четвёртый цикл прошёл без вопросов и ошибок. Опубликовано 22.09.2026, README со скриншотами.

# Устройство кодовой базы

«Кино База» — персональная база фильмов одного зрителя: сетка постеров, справочные данные о тайтлах и их создателях, личные оценки владельца и материалы, собранные агентом. Этот файл — карта репозитория: как запрос превращается в страницу, где что лежит, какой командой наполняется база и чем всё проверяется. Он рассчитан и на человека, который открыл проект впервые, и на агента, которому нужно понять, куда класть правку.

Стек: Next.js 16 (App Router), React 19, TypeScript в строгом режиме, Tailwind 4, SQLite через `better-sqlite3` и Drizzle, тесты на vitest с Testing Library, скрипты наполнения на `tsx`. Визуальная система описана отдельно, в `DESIGN.md`.

## Как это устроено

Все страницы — серверные компоненты и объявлены `dynamic = 'force-dynamic'`: кеша между запросом и базой нет, каждый запрос читает данные заново. Страница получает состояние отбора из адреса, разбирает его модулями `src/lib/url-state.ts` и `src/lib/filters.ts`, берёт данные у репозитория (`src/lib/films-repo.ts`, `src/lib/people-repo.ts`), а репозиторий обращается к клиенту базы из `src/db/index.ts`. Клиент создаётся один раз на процесс, при создании накатывает миграции и отдаёт типизированные таблицы из `src/db/schema.ts`. Вёрстка собирается из компонентов `src/components/`; клиентскими объявлены только те, без которых не обойтись, — переключатели, редактор комментария, полноэкранный просмотр постера.

Данные приезжают двумя разными путями, и путать их нельзя. Справочная часть — названия, даты, рейтинги, создатели, аннотации, теги, сезоны, досье, персоналии — живёт в файлах `content/*.json` и попадает в базу только скриптами наполнения из `scripts/`. Личные поля — отметки «посмотрел» и «хочу посмотреть», оценка, звёздочка вкуса, комментарий — существуют только в базе и правятся через интерфейс. Отсюда два источника правды: для справки правдой остаётся файл, потому что правку, сделанную прямо в базе, молча откатит следующий прогон скрипта; для личных полей правдой остаётся база, потому что в файлы они не выгружаются и ни один скрипт наполнения их не трогает. Формы добавления тайтлов в интерфейсе нет: записи заводит агент, редактируя файлы данных.

Владельца сайт узнаёт по куке. Чистая арифметика признака лежит в `src/lib/owner.ts` — имена кук и сверка значения куки с секретом `OWNER_TOKEN` постоянным по времени сравнением; чтение куки из запроса и решение «кто ты» — в `src/lib/session.ts`. Вне боевой сборки `ownerSession()` всегда отвечает «владелец»: локальная база — личная копия на своей же машине, гостя там нет, и требовать вход незачем. В production признак держится на куке, которую ставит маршрут `/owner/login` и снимает `/owner/logout`. Поверх этого есть режим «глазами гостя»: кука `kinobase_guest_view` не отменяет сессию, но `viewerIsOwner()` в нём отвечает «нет» — и отвечают так все сразу, страницы, подвал и страж серверного действия. Поэтому проверка «как это выглядит для читателя» проверяет поведение, а не вёрстку. Гостю секция личных полей не рендерится вовсе, а не прячется стилями; исключение — комментарий владельца: он написан для читателя и виден всем, оставаясь личным полем по способу правки.

Путь записи личных полей ровно один — серверное действие `updatePersonalAction` из `src/app/actions.ts`, которое сперва спрашивает `viewerIsOwner()` (до разбора данных и до поиска фильма, чтобы по виду ответа нельзя было узнать даже о существовании записи), а затем зовёт `updatePersonal` из `src/lib/films-repo.ts`. Там же, в репозитории, живут правила, и достаются они каждой поверхности правки даром: оценка означает просмотр (поставленная оценка сама поднимает отметку «посмотрел»), отметки «посмотрел» и «хочу посмотреть» взаимоисключающи (поднятая снимает вторую, снятая не поднимает ничего), невышедший тайтл нельзя ни отметить просмотренным, ни оценить, а снятая отметка «посмотрел» уносит с собой оценку. Форму входных данных проверяет `src/lib/validate.ts` по конвенции проекта: валидатор возвращает `null` при успехе либо код ошибки. Новая поверхность правки должна переиспользовать действие, а не писать похожее.

## Маршруты

| Путь | Что показывает | Откуда данные |
|---|---|---|
| `/` — `src/app/page.tsx` | Сетка постеров: табы статусов, панель фильтров, строка применённого отбора; в табе «Ждём» вместо сетки — таймлайн по месяцам | `listFilms` и `countPeople` из базы; статус, отбор и сортировка считаются из адреса и «сегодня» |

| `/people` — `src/app/people/page.tsx` | Указатель персоналий с отбором по ролям | `listPeople`, `filmCountsByPerson`, плюс `listFilms` для счётчиков табов в шапке |
| `/people/[slug]` — `src/app/people/[slug]/page.tsx` | Страница создателя: справка, фотография с указанием автора, творческий метод, разбор работ, галерея фильмов из базы, источники | `getPersonBySlug`, `filmsOfPerson`, `listFilms` — по нему работа связывается с карточкой по оригинальному названию |
| `/owner/login` | Ставит куку владельца и возвращает на главную; пароль не проверяет — до маршрута доходят только пропущенные веб-сервером | `OWNER_TOKEN` из окружения |
| `/owner/logout` | Снимает куку владельца | — |
| `/owner/guest-view` | Включает режим «глазами гостя»; без сессии владельца отвечает редиректом на главную | Параметр `back`, принимается только внутренний путь |
| `/owner/owner-view` | Снимает режим «глазами гостя» | Параметр `back` |

Рядом с маршрутами: `src/app/layout.tsx` — корневая разметка, шрифты, метаданные и Open Graph, общая кнопка возврата наверх; `src/app/actions.ts` — единственное серверное действие проекта; `src/app/globals.css` — токены палитры и базовые стили Tailwind; `src/site.config.ts` — настройки конкретной базы (заголовок, адрес, имя владельца, ссылка на его блог, описание).

## База

Схема — `src/db/schema.ts`, три таблицы.

**`films`** — тайтл целиком: русское и оригинальное названия, путь к постеру, дата выхода, сезоны сериала (сколько вышло, номер и дата следующего — дата допускает точность до месяца), рейтинги и идентификаторы IMDb и Кинопоиска, аннотация, создатели строками и состав исполнителей массивом, теги, три блока досье с источниками и датой поиска, дата заведения записи — и личные поля: «посмотрел», «хочу посмотреть», оценка, звёздочка вкуса, комментарий. Блок досье, равный `null`, означает «не собран»; пустой массив запрещён валидатором, чтобы не появилось третьего неотличимого состояния.

**`people`** — создатель: слаг, имена, фотография с обязательным указанием автора, даты и место рождения, роли, основные работы, ссылки, идентификаторы, справка, творческий метод, разбор работ, источники и дата поиска. Личных полей у таблицы нет и не будет: персоналию нельзя оценить, и запрет держится схемой, а не вёрсткой.

**`film_people`** — связь фильма и человека. Первичный ключ тройной: один человек бывает в одном фильме и режиссёром, и сценаристом, и это две разные связи.

Миграции лежат в `drizzle/` вместе со снимками схемы, их десять. Отдельной команды наката нет: `createDb` из `src/db/index.ts` прогоняет их сам при создании клиента, поэтому и сайт, и любой скрипт получают базу нужной версии. После правки `schema.ts` новая миграция генерируется командой `npm run db:generate`; дописывать в миграцию `UPDATE` руками нельзя — повторная генерация его сотрёт.

Путь к базе берётся из переменной `DB_PATH`, а без неё — `data/kinobaza.db` рядом с кодом. Переменная нужна не только серверу: живые проверки в браузере пишут в рабочую базу, поэтому гонять их полагается на отдельной, например `DB_PATH=/tmp/kinobaza-test.db`. Файловая база открывается в режиме WAL, чтобы чтение не ждало запись, и с ожиданием вместо ошибки «база занята»; для базы в памяти, на которой работают тесты, оба параметра бессмысленны и не ставятся. Из режима WAL следует важное практическое: копию базы нельзя снимать обычным `cp` — часть данных лежит в файлах `-wal` и `-shm`, и копия выйдет отставшей. Либо копировать все три файла вместе, либо снимать копию командой `sqlite3 kinobaza.db ".backup копия.db"`.

## Наполнение и проверки

Скрипты лежат в `scripts/`, команды объявлены в `package.json`. Общее у всех одно: сначала проверяется весь файл данных, и только потом открывается база — ошибка в одной записи не должна оставить базу наполненной наполовину. **Личных полей скрипты не трогают вовсе**: ни один из них не пишет в оценку, звёздочку, комментарий и отметки.

| Команда | Что делает | Что читает |
|---|---|---|
| `npm run seed` | Наполняет пустую базу; на непустой останавливается, чтобы не затереть личное | `content/films-data.json` |
| `npm run add-films` | Доливает в непустую базу тайтлы, которых в ней ещё нет; существующих не трогает | `content/films-data.json` |
| `npm run refresh-films` | Переносит справочные поля уже занесённых тайтлов из файла в базу. По умолчанию только показывает, что изменится; записывает с флагом `-- --go` | `content/films-data.json`, перечень колонок из `src/lib/refresh.ts` |
| `npm run tag-films` | Проставляет теги всем тайтлам базы | `content/tags-data.json` |
| `npm run fill-seasons` | Записывает сезоны сериалов | `content/seasons-data.json` |
| `npm run fill-dossiers` | Записывает три блока досье, источники и дату поиска | `content/dossier-data.json` |
| `npm run fill-people` | Заводит персоналии и связи с фильмами по оригинальному названию | `content/people-data.json` и уже занесённые тайтлы |
| `npm run check-data` | Сводит файлы данных между собой: ключи, дубли, расхождение тегов и сезонов, ссылки, постеры. Базу не открывает | все файлы `content/` |
| `npm run check-db` | Ищет в живой базе состояния, которые правила запрещают, а данные всё-таки содержат: обе отметки разом, оценка у непросмотренного | база |
| `npm run check-facts` | Проверяет таблицы фактов в архивах заходов по контракту и считает их | `research/` |
| `npm run check-dossier` | Механическая проверка готовых досье и справочных полей карточки | `content/dossier-data.json`, `content/films-data.json`, архивы `research/` |
| `npm run check-dossier-one <файл>` | Те же правила, но на одной записи в отдельном файле — так проверяет себя агент, пишущий свой файл | указанный файл |
| `npm run keys-check <файл>` | Форма блока «Важные вещи о фильме»: ровно семь пунктов, объём, полужирный лид, отсутствие ссылок и слов про приём | указанный файл |
| `npm run run-stats` | Замер заходов: страницы архива, строки таблиц фактов, объём текста, врезки, источники | `research/`, `content/dossier-data.json` |
| `npm run archive-slugs` | Печатает соответствие «оригинальное название — папка архива»; ничего не пишет | `content/dossier-data.json` |

Первое наполнение с нуля идёт строго в таком порядке, и порядок не случаен — `fill-people` ищет фильмы по оригинальному названию и упадёт, если тайтлы ещё не заведены:

```
npm run check-data
npm run seed
npm run add-films
npm run refresh-films -- --go
npm run tag-films
npm run fill-seasons
npm run fill-dossiers
npm run fill-people
npm run check-db
```

Две вещи, о которые спотыкаются чаще всего. Первая: **теги и сезоны продублированы** между `content/films-data.json` и файлами `content/tags-data.json` и `content/seasons-data.json` — менять нужно оба места и прогонять `npm run check-data`, иначе правка одного молча откатится следующим прогоном. Вторая: **фильм ищется по оригинальному названию**, а не по русскому, — одинаковые русские названия в базе норма, и ключ на них разошёлся бы молча. Ключ живёт одной функцией в `src/lib/film-key.ts`, и все скрипты берут его оттуда.

Общая обвязка скриптов — в `scripts/lib/`: `db.ts` открывает базу и читает файл данных, `data-files.ts` хранит единственный список путей к файлам `content/`, `facts-archive.ts` обходит архивы `research/` и сопоставляет папку с тайтлом.

## Тексты и скиллы

Правила, по которым пишутся агентские тексты, лежат в `research/` и здесь не пересказываются: `SOURCING.md` — как ищем, `VERIFICATION.md` — как проверяем и как устроена таблица фактов, `CARD-FORMAT.md` — форма справочной карточки, `DOSSIER-FORMAT.md` — форма досье и трёх его блоков, `CREATOR-FORMAT.md` — форма страницы создателя, `SEARCH-PROFILE.md` — какие поисковые инструменты доступны. Рядом, в корне, `viewer-profile.md` — зрительский профиль владельца, на который опирается рубрика «Почему это может быть интересно мне»; пока файл пуст, рубрика не пишется.

Наполняют базу три скилла в `.agents/skills/`: `film-card` — справочная карточка тайтла, `film-dossier` — досье к фильму, `creator-dossier` — персоналия и творческий метод. Там же лежат вспомогательные `exa-tabstack-search` и `full-file-read`.

## Тесты

Тесты лежат в `tests/`, по файлу на модуль или компонент, плюс `helpers.ts`, который собирает тайтл с пустыми полями. Среда — jsdom, конфигурация в `vitest.config.mts` и `vitest.setup.ts`. Тест здесь — контракт: он описывает поведение, а не реализацию, и проверяет его через публичный интерфейс. Быстрые и детерминированные: в сеть не ходят, база — SQLite в памяти, «сегодня» передаётся аргументом, а не берётся из часов.

Гонять их следует последовательно:

```
npx vitest run --no-file-parallelism
```

Причина в том, что под нагрузкой параллельный прогон выходит с нулевым кодом, не собрав часть файлов, — и неполный прогон выглядит успехом. Поэтому смотреть надо не на цвет, а на число собранных файлов и тестов. Обычный `npm test` запускает тот же vitest параллельно и годится, когда машина свободна.

Чего тесты не проверяют: **вёрстку**. В jsdom Tailwind не загружен, и классы остаются классами, ничего не раскладывая, — поэтому любое изменение вёрстки требует живого прогона в браузере. Тесты доказывают соответствие правилам, но не полноту самих правил: дыры в них находит живое пользование.

## Отличия от проекта автора

Эта версия собрана из личного проекта и отчуждена от владельца — всё, что было привязано к конкретному человеку, либо снято, либо вынесено в настройки.

- **Снята страница «О проекте»** — это был авторский текст от первого лица.
- **Снята админка** — таблица со сводным состоянием материалов и выгрузкой профиля. Личные поля правятся на карточке фильма, и поверхность правки осталась одна.
- **Снята плашка со ссылкой на разборы владельца** в его телеграм-канале вместе со словарём этих ссылок.
- **Личные константы вынесены в `src/site.config.ts`** — заголовок, адрес, имя владельца, ссылка на его блог и описание сайта. Это единственный файл в `src/`, который правится под конкретного владельца; остальной код берёт значения через `src/lib/site.ts`.
- **Файлы данных переехали в `content/`** и получили общий дом — раньше они лежали в папках версий. Единственный список путей — `scripts/lib/data-files.ts`.
- **Проверка правовой рамки стала общей.** Содержание пометок задаёт юрисдикция владельца, поэтому кода, знающего конкретные формулировки, здесь нет: проверяется только форма — если в тексте блока стоит звёздочка-отсылка, в нём же должен быть абзац-сноска, начинающийся с «`* `».
- Вместе с ними ушли внутренние документы процесса автора; из сопроводительного в репозитории остались `DESIGN.md` (визуальная система), `docs/posters.md` (где и как искать постеры, какие два размера кладутся), `AGENTS.md` (автоматически обновляемая памятка по Next.js), `.env.example` (переменные окружения) и `deploy.sh` с `deploy.env.example` — выкатка на свой сервер: база на сервере остаётся источником правды и скриптом не переносится, поэтому новые тайтлы доливаются на нём отдельно, теми же командами наполнения.

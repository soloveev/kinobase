# Свой сервер: от чистой машины до HTTPS

Кино База — обычное приложение Next.js с базой SQLite в файле. Работает оно так: на сервере лежит код, там же он собирается (`npm ci && npm run build`) и запускается командой `next start` под управлением systemd. Приложение слушает только петлю (`127.0.0.1`), а наружу смотрит nginx — он же отдаёт HTTPS с сертификатом Let's Encrypt, раздаёт статику и спрашивает пароль на входе владельца. База живёт вне каталога с кодом и выкаткой не заменяется: она и есть источник правды.

Ничего специфичного для конкретного хостинга здесь нет — годится любая машина с Ubuntu 24.04 и публичным адресом. Одного ядра и гигабайта памяти хватает, но со сборкой на такой машине помогает файл подкачки: `next build` — самая прожорливая минута за всю жизнь сервера.

Шаблоны конфигурации, которые упоминаются ниже, лежат рядом, в `ops/`. Это заготовки с плейсхолдерами, а не готовые файлы: подставить значения и положить на сервер — часть установки.

## Что подставлять вместо плейсхолдеров

| Плейсхолдер | Что это | Обычное значение |
|---|---|---|
| `${DOMAIN}` | домен сайта | `kinobase.example.com` |
| `${SERVER_IP}` | публичный адрес сервера | — |
| `${SSH_HOST}` | ssh-алиас или `root@${SERVER_IP}` | `kinobase-srv` |
| `${REMOTE_DIR}` | каталог с кодом на сервере | `/var/www/kinobase` |
| `${DEPLOY_USER}` | системный пользователь службы | `kinobase` |
| `${TZ}` | часовой пояс владельца | `Europe/Moscow` |
| порт приложения | локальный порт `next start` | `3001` |

Два уточнения, которые сэкономят час.

Имя `${DEPLOY_USER}` и порт задаются в `deploy.env` (`DEPLOY_USER`, `APP_PORT`; по умолчанию `kinobase` и `3001`): `deploy.sh` берёт их оттуда, когда отдаёт код пользователю службы после сборки и проверяет ответ приложения.

Порт встречается в трёх местах — в юните службы, в nginx-хосте и в `deploy.env`. Меняется он во всех трёх или ни в одном.

## Раскладка на сервере

```
${REMOTE_DIR}/                      код, зависимости и сборка (владелец ${DEPLOY_USER})
/var/lib/kinobase/kinobaza.db       база — источник правды (${DEPLOY_USER}, 600)
/var/backups/kinobase/              копии базы: ночные и предвыкаточные
/etc/kinobase.env                   OWNER_TOKEN (root, 600)
/etc/nginx/.htpasswd-kinobase       пароль HTTP на вход владельца
/etc/systemd/system/kinobase.service
/etc/nginx/sites-available/kinobase
/usr/local/bin/kinobase-backup.sh   ночная копия по cron
```

База лежит отдельно от кода намеренно. Выкатка переносит рабочее дерево с `rsync --delete`, и всё, что окажется внутри каталога кода, рано или поздно этим `--delete` снесёт. Вне каталога базе ничего не грозит: скрипт выкатки её не видит и не трогает.

## 1. Доступ и подготовка системы

Начинается всё с ключа. На своей машине:

```bash
ssh-copy-id root@${SERVER_IP}
```

Дальше удобно завести алиас, чтобы не набирать адрес каждый раз. В `~/.ssh/config`:

```
Host kinobase-srv
    HostName ${SERVER_IP}
    User root
    IdentityFile ~/.ssh/id_ed25519
```

Именно это имя потом пойдёт в `deploy.env` как `SSH_HOST`. Подключение идёт под root: `deploy.sh` перезапускает службу и меняет владельца файлов, то есть делает вещи, на которые обычному пользователю нужен `sudo`. Если политика сервера требует непривилегированного входа, заводите пользователя с беспарольным `sudo` и дописывайте `sudo` в те три команды внутри `deploy.sh`, которые обращаются к системе.

Дальше — на сервере. Файл подкачки, если памяти гигабайт или два:

```bash
fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
```

Node из репозитория Ubuntu не годится: там версия старше, чем требует Next 16 (ему нужен Node 20.9 и новее, а практически — действующий LTS, 22 или 24). Ставится он из NodeSource:

```bash
apt update && apt install -y ca-certificates curl gnupg
curl -fsSL https://deb.nodesource.com/setup_22.x | bash -
apt install -y nodejs build-essential sqlite3 nginx certbot python3-certbot-nginx
node -v && npm -v && sqlite3 --version
```

`build-essential` нужен на случай, если `better-sqlite3` не найдёт готовый бинарник под эту связку Node и Linux и решит собираться из исходников.

Можно и через nvm, но тогда имейте в виду: nvm ставит Node внутрь домашнего каталога пользователя, а юнит службы запускает `/usr/bin/node`. С nvm путь в `ExecStart` придётся заменить на фактический (`/root/.nvm/versions/node/v22.*/bin/node` или аналогичный у вашего пользователя) — и не забывать про это при каждом обновлении Node. Для службы, которую поднимает systemd, NodeSource спокойнее.

## 2. Пользователь и каталоги

Приложение работает под отдельным системным пользователем без оболочки входа: Node не должен ходить под root.

```bash
useradd --system --shell /usr/sbin/nologin --home ${REMOTE_DIR} ${DEPLOY_USER}

mkdir -p ${REMOTE_DIR} /var/lib/kinobase /var/backups/kinobase /var/www/certbot
chown -R ${DEPLOY_USER}:${DEPLOY_USER} ${REMOTE_DIR} /var/lib/kinobase
chmod 750 /var/lib/kinobase
chmod 700 /var/backups/kinobase
```

Каталог `/var/www/certbot` понадобится через несколько шагов — в нём Let's Encrypt оставляет файл для проверки домена.

Одно про права, о чём легко забыть: nginx читает статику и постеры прямо из `${REMOTE_DIR}`, а работает он под своим пользователем (`www-data`). Значит, каталоги по пути должны быть проходимы для всех — режим `755` у `${REMOTE_DIR}` и выше. Если `chmod 750` случайно доедет до каталога кода, сайт начнёт отдавать страницы без стилей и без постеров.

## 3. Секрет владельца

Разграничение прав в Кино Базе устроено просто. Маршрут `/owner/login` кладёт в куку значение переменной `OWNER_TOKEN`, а дальше каждая страница сверяет куку с той же переменной и решает, показывать ли поля для правки. Пароля сам маршрут не спрашивает — пароль спрашивает nginx перед ним. Поэтому секрет нужен в двух местах: на сервере в окружении службы и в локальном `.env.local`, причём одним и тем же значением.

```bash
install -m 600 -o root -g root /dev/null /etc/kinobase.env
printf 'OWNER_TOKEN=%s\n' "$(openssl rand -hex 24)" > /etc/kinobase.env
cat /etc/kinobase.env     # это же значение — в локальный .env.local
```

Образец с пояснениями — `ops/kinobase.env.example`. С кодом этот файл не едет никогда: `deploy.sh` исключает из переноса всё, что начинается на `.env`.

Пустая или отсутствующая переменная означает «владельца нет»: вход просто перестанет работать, и сайт для всех станет читательским. Это сознательно — опечатка в конфигурации должна запирать дверь, а не открывать.

## 4. Первый перенос кода и сборка

Выкаточный скрипт для первого раза не подходит: он в конце перезапускает службу, которой пока нет. Первый перенос делается вручную, теми же исключениями, что и потом:

```bash
cd <локальный каталог проекта>
rsync -az --delete \
  --exclude '.git' --exclude 'node_modules' --exclude '.next' --exclude '.env*' \
  --exclude 'data' --exclude 'research/*/' --exclude 'deploy.env' \
  --exclude '*.tsbuildinfo' --exclude '.DS_Store' \
  ./ ${SSH_HOST}:${REMOTE_DIR}/
```

Дальше — зависимости и сборка на сервере:

```bash
ssh ${SSH_HOST} "cd ${REMOTE_DIR} && npm ci --no-audit --no-fund && npm run build"
```

Собираем именно на сервере, а не у себя: `better-sqlite3` — нативный модуль, и бинарник, собранный под macOS, на Linux не запустится.

Переменную `NODE_ENV=production` в этой команде выставлять не надо. Сборке нужны и девелоперские зависимости — TypeScript, Tailwind, `tsx`, — а `npm ci` при `NODE_ENV=production` их пропустит, и сборка упадёт на отсутствующем пакете.

## 5. Первое наполнение базы

Схему базы создаёт само приложение: миграции применяются при открытии соединения. Поэтому достаточно запустить сид — он создаст файл, накатит миграции и зальёт справочные записи из `content/`:

```bash
ssh ${SSH_HOST} "cd ${REMOTE_DIR} && DB_PATH=/var/lib/kinobase/kinobaza.db npm run seed"
```

`DB_PATH` здесь обязателен: без него скрипт полезет в `data/kinobaza.db` внутри каталога кода, то есть заведёт вторую базу, которую никто не читает и которую снесёт первая же выкатка.

Сид работает только с пустой базой и останавливается, увидев в ней фильмы, — так личные поля защищены от случайного повторного запуска.

Сразу после любого скрипта, запущенного от root, файлы базы принадлежат root — служба писать в них не сможет. Владельца нужно вернуть, и обязательно вместе со спутниками `-wal` и `-shm`:

```bash
ssh ${SSH_HOST} "chown ${DEPLOY_USER}:${DEPLOY_USER} /var/lib/kinobase/kinobaza.db* && chmod 600 /var/lib/kinobase/kinobaza.db"
```

Если база уже есть на другой машине и её нужно перенести, копия снимается не `cp`, а `sqlite3`:

```bash
sqlite3 <старая база> ".backup 'kinobaza-перенос.db'"
scp kinobaza-перенос.db ${SSH_HOST}:/var/lib/kinobase/kinobaza.db
```

Причина та же, что и у ночных копий: база работает в режиме WAL, и обычное копирование файла даёт снимок без последних записей. Отстающий он при этом молча — файл выглядит целым. После переноса стоит сверить числа на обеих сторонах, хотя бы `select count(*) from films` и число заполненных личных полей.

## 6. Служба

Шаблон юнита — `ops/kinobase.service`. Подставляем значения и ставим на место:

```bash
# на сервере, в каталоге кода: слева — плейсхолдер из шаблона, справа — ваше значение
cd ${REMOTE_DIR}
sed -e 's|${DEPLOY_USER}|kinobase|g' \
    -e 's|${REMOTE_DIR}|/var/www/kinobase|g' \
    -e 's|${TZ}|Europe/Moscow|g' \
    ops/kinobase.service > /etc/systemd/system/kinobase.service

systemctl daemon-reload && systemctl enable --now kinobase && systemctl is-active kinobase
```

Что в юните заслуживает внимания. `TZ` задаёт часовой пояс: от него зависит, какой день сайт считает сегодняшним, а «сегодня» решает, вышел фильм или ещё нет. `-H 127.0.0.1` в строке запуска прячет приложение от внешнего мира — снаружи к нему можно попасть только через nginx. `MemoryMax=500M` — страховка: процесс с утечкой убьёт себя и перезапустится, а не заберёт машину целиком. `EnvironmentFile` подтягивает тот самый `/etc/kinobase.env`. И `ReadWritePaths` перечисляет два каталога, куда службе вообще можно писать: база и кэш сборки Next.

Проверяем, что приложение отвечает на своей петле:

```bash
ssh ${SSH_HOST} "curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3001/"
```

Ожидаемый ответ — `200`. Если нет, логи смотрятся так:

```bash
ssh ${SSH_HOST} "journalctl -u kinobase -n 50 --no-pager"
```

## 7. Имя сайта, nginx и HTTPS

A-запись `${DOMAIN}` → `${SERVER_IP}` заводится в панели регистратора домена; агент этого сделать не может, это шаг владельца. Прежде чем идти дальше, стоит дождаться, пока запись разойдётся:

```bash
dig +short ${DOMAIN}
```

Пока команда не печатает `${SERVER_IP}`, выпускать сертификат бессмысленно: проверка Let's Encrypt придёт не на ваш сервер.

Шаблон хоста — `ops/nginx-kinobase.conf`. Первый заход делается в два приёма, потому что блока 443 не существует до сертификата: файлов `/etc/letsencrypt/live/${DOMAIN}/` ещё нет, и nginx с таким конфигом просто не запустится.

Сначала кладём файл, закомментировав в нём весь блок `listen 443`:

```bash
cd ${REMOTE_DIR}
sed -e 's|${DOMAIN}|kinobase.example.com|g' \
    -e 's|${REMOTE_DIR}|/var/www/kinobase|g' \
    ops/nginx-kinobase.conf > /etc/nginx/sites-available/kinobase
# отредактировать: закомментировать блок с listen 443 целиком
ln -s /etc/nginx/sites-available/kinobase /etc/nginx/sites-enabled/kinobase
nginx -t && systemctl reload nginx
```

Порядок здесь важен, и вот почему. Блок с вашим именем должен появиться в nginx **до** запуска certbot. Если на сервере живёт ещё один сайт, запрос на незнакомое имя попадёт в первый по списку блок — то есть к соседу, — и проверка домена уедет соседским редиректом, а сертификат не выпустится.

Пароль на вход владельца заводится тем же заходом:

```bash
apt install -y apache2-utils
htpasswd -c /etc/nginx/.htpasswd-kinobase <имя пользователя>
chown root:www-data /etc/nginx/.htpasswd-kinobase && chmod 640 /etc/nginx/.htpasswd-kinobase
```

Это пароль только для одного адреса — `/owner/login`. Всё остальное открыто для чтения всем.

Сертификат:

```bash
certbot certonly --webroot -w /var/www/certbot -d ${DOMAIN} --agree-tos -m <почта> --no-eff-email
```

Теперь раскомментируем блок 443 и перезагружаем nginx. Заодно стоит проверить, есть ли на месте файлы `/etc/letsencrypt/options-ssl-nginx.conf` и `/etc/letsencrypt/ssl-dhparams.pem`: их кладёт certbot, когда работает своим плагином к nginx, а после `certonly --webroot` их может не оказаться. В шаблоне соответствующие строки закомментированы — если файлы появились, их можно включить.

```bash
nginx -t && systemctl reload nginx
```

Certbot ставит таймер обновления сам, так что продлевать сертификат руками не нужно. Проверить, что механизм жив, можно так:

```bash
systemctl list-timers | grep certbot
certbot renew --dry-run
```

Наконец, ответ снаружи:

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://${DOMAIN}/         # 200
curl -s -o /dev/null -w '%{http_code}\n' https://${DOMAIN}/owner/login   # 401 — так и надо
```

`401` на входе владельца — признак того, что Basic Auth работает. Откройте этот адрес в браузере, введите пароль — и вас вернёт на главную уже владельцем, с полями для правки оценок. Проверить, что кука действительно легла, проще всего по подвалу: у владельца там есть «Выйти».

## Как выкатывать дальше

Всё последующее — одной командой. Адрес сервера и пути к нему живут в `deploy.env` в корне репозитория; в гит он не едет, образец — `deploy.env.example`:

```bash
cp deploy.env.example deploy.env
# заполнить SSH_HOST, REMOTE_DIR, REMOTE_DB, BACKUPS, SERVICE, DOMAIN, SERVER_IP
```

Дальше:

```bash
./deploy.sh              # dry-run: печатает, что изменится, и ничего не трогает
./deploy.sh --go         # выкатка, спросит подтверждение с клавиатуры
./deploy.sh --go --yes   # без вопроса — для агента, у которого клавиатуры нет
```

Скрипт прогоняет проверки (тесты, типы, линтер, файлы данных, состояние базы) и останавливается на первом красном — флага «пропустить» у него нет намеренно. Потом переносит код, снимает копию базы, ставит зависимости, собирает, перезапускает службу и проверяет ответ — снаружи и изнутри.

Что важно помнить про выкатку:

- **локальную базу она не везёт.** База на сервере — источник правды, `deploy.sh` её не касается вовсе. Новый фильм, досье или страница создателя, заведённые у вас на машине, на сайте сами не появятся: они приедут файлами данных, а в базу их зальют скрипты наполнения, запущенные на сервере.
- **личные поля живут только на сервере.** Оценки, звёздочки, отметки и комментарии ставятся через сайт и пишутся в боевую базу. Локальная копия про них знает лишь то, что было на момент, когда её забрали. Никакой скрипт наполнения личные поля не трогает — единственный путь записи проходит через серверное действие сайта.
- **`rsync` везёт рабочее дерево, а не то, что в гите.** Незакоммиченный файл уедет на сервер, если он не попал в список исключений внутри `deploy.sh`. Перед выкаткой стоит посмотреть `git status` и сверить с этим списком.
- **секрет не едет с кодом:** `.env*` в исключениях, служба берёт `OWNER_TOKEN` из своего окружения.

## Как доливать новые тайтлы в боевую базу

Справочные данные лежат файлами в `content/`, и на сервер они приезжают обычной выкаткой. В базу их переносят скрипты наполнения — запускаются они на сервере, всегда с указанием `DB_PATH`:

```bash
ssh ${SSH_HOST} "cd ${REMOTE_DIR} && DB_PATH=/var/lib/kinobase/kinobaza.db npm run add-films"
```

Порядок, если менялось не только появление новых тайтлов:

```
add-films      новые тайтлы (дублем считается совпадение оригинального названия)
refresh-films  обновлённая справка у тех, кто уже в базе
tag-films      теги
fill-seasons   сезоны сериалов
fill-dossiers  блоки досье
fill-people    персоналии
check-db       проверка: запрещённых состояний в базе нет
```

Каждый — той же формы командой, с тем же `DB_PATH`. Запускать нужно не все подряд, а те, чьи данные менялись; порядок между собой они сохраняют, потому что поздние опираются на записи, заведённые ранними.

Перезапускать службу после долива не нужно: страницы сайта динамические, каждый запрос читает базу заново. Обновите вкладку — новый фильм на месте.

И снова про владельца файлов. Скрипты, запущенные от root, оставляют файлы базы принадлежащими root, и служба после этого писать в базу не сможет — сайт будет показывать страницы, но откажется сохранять оценки. Завершайте долив возвратом владельца:

```bash
ssh ${SSH_HOST} "chown ${DEPLOY_USER}:${DEPLOY_USER} /var/lib/kinobase/kinobaza.db*"
```

## Копии базы

Ночную копию снимает `ops/backup-db.sh` — раз в сутки, командой `sqlite3 .backup`, с ротацией в четырнадцать дней. Устанавливается он один раз:

```bash
# на сервере, из каталога кода
cd ${REMOTE_DIR}
install -m 700 ops/backup-db.sh /usr/local/bin/kinobase-backup.sh
crontab -e
```

Строка задания:

```
0 4 * * * /usr/local/bin/kinobase-backup.sh >> /var/log/kinobase-backup.log 2>&1
```

Копии складываются в `/var/backups/kinobase/`, туда же `deploy.sh` кладёт снимок, который снимает перед каждой выкаткой, — ротация подбирает и их. Наутро в логе должна появиться строка с именем файла и числом тайтлов; пустой лог означает, что копий нет, а не что всё хорошо.

Свежую копию себе на машину забирает готовый скрипт — он читает тот же `deploy.env`:

```bash
./scripts/pull-db.sh
```

Скрипт снимает согласованный снимок на сервере, забирает его во временный файл, печатает путь и считает по нему тайтлы, оценки, звёздочки и комментарии. Рабочую локальную базу он не перезаписывает — только показывает команду, которой это сделать, если вы действительно этого хотите.

Восстановление из копии — ручная операция, и торопиться в ней не стоит:

```bash
ssh ${SSH_HOST} "systemctl stop kinobase"
ssh ${SSH_HOST} "sqlite3 /var/lib/kinobase/kinobaza.db '.backup \"/var/backups/kinobase/до-восстановления.db\"'"
ssh ${SSH_HOST} "cp /var/backups/kinobase/<нужная копия>.db /var/lib/kinobase/kinobaza.db \
  && rm -f /var/lib/kinobase/kinobaza.db-wal /var/lib/kinobase/kinobaza.db-shm \
  && chown ${DEPLOY_USER}:${DEPLOY_USER} /var/lib/kinobase/kinobaza.db"
ssh ${SSH_HOST} "systemctl start kinobase"
```

Копия текущего состояния снимается первой строкой не для порядка: восстановление «не из того файла» — самый обычный способ потерять неделю оценок.

## Когда что-то не работает

Первым делом — логи приложения:

```bash
ssh ${SSH_HOST} "journalctl -u kinobase -n 50 --no-pager"
ssh ${SSH_HOST} "systemctl status kinobase"
```

Дальше по симптому:

- **502 от nginx** — приложение не отвечает на своей петле. Смотрим, живо ли оно: `systemctl is-active kinobase` и `curl http://127.0.0.1:3001/` с сервера. Чаще всего это упавшая сборка или несовпавший порт.
- **сайт без стилей, постеры не открываются** — nginx не может прочитать файлы из каталога кода. Проверяем права на `${REMOTE_DIR}` и вниз по пути: `www-data` нужен проход.
- **оценки не сохраняются, страницы при этом открываются** — база доступна только на чтение. Почти всегда это файлы, оставшиеся от root после скриптов наполнения: возвращаем владельца командой из раздела про долив.
- **владелец не узнаётся, поля для правки пропали** — разошлись `OWNER_TOKEN` в `/etc/kinobase.env` и значение в куке. Перевыпустить секрет, перезапустить службу и войти заново через `/owner/login`.
- **nginx не перезагружается** — `nginx -t` печатает файл и строку. После сертификата самая частая причина — блок 443, оставшийся закомментированным наполовину.
- **приложение периодически перезапускается** — упёрлось в `MemoryMax`. Видно в `journalctl` по строке про OOM; лечится поднятием лимита в юните.
